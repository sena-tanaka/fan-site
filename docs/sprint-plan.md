## 2. ユーザーストーリーの優先順位付け

### 2.1 MVP をどう決めたか

26h で作れるのは、土台（環境構築・DB・レイアウト 11h）のほかに約 15h 分です。
その 15h で、**公式サイトとして最低限そろっていてほしい「チームとメンバーを知る」「出演予定を確かめる」「チームに連絡する」** の3つを作ります。いずれもログインなしで誰でも使える機能です。

- **出演スケジュール（US-01）**：ヒアリングで一番多かった困りごと「いつどこでパフォーマンスが見られるか分からない」を解決する
- **メンバー一覧（US-03）・チーム紹介（US-02）**：「推しのダンサーのことをもっと知りたい」「どんなチームか知ったうえで応援したい」というファンの動機に応える。どちらも小さく作れる
- **お問い合わせ（US-06）**：公式サイトの窓口を一本化する（[要件定義書 1.3](./requirements.md#13-目的ゴール)）うえで、ファンがチームに直接連絡できる手段は欠かせない
- 購入（US-05・US-08）は価値が高いが、グッズ購入だけで 10.5h かかり、上の4つと両立できないため今回は入れない
- 会員登録・ログイン（US-07）は、会員向けの機能（チケット・おみくじ・ブログ）を作るときに初めて必要になる。MVP には会員向け機能がないので後回しにする

### 2.2 優先順位の決め方

1. **今回のリリース（3スプリント・26h）に対して MoSCoW で分ける**
   要件定義書の優先度（必須・推奨・任意）は「サービス全体」で見たもの、ここでの MoSCoW は「この 26h で何を作るか」で見たものです。

   | MoSCoW | 意味 | 該当 |
   |--------|------|------|
   | Must | 26h の中で必ず作る（MVP） | US-01、US-03、US-06、US-02、土台の技術タスク |
   | Should | 予定より早く終わったら作る | US-04 |
   | Could | 今回は作らず、次のリリースの候補にする | US-05、US-07〜21 |
   | Won't | 今回もこの先も作らない | スマホアプリ・実際の配送（[制約条件](./requirements.md#6-制約条件) C-10, C-11） |

2. **並べ方の基準**
   - **ファンにとっての価値**：公式サイトとしての基本（知る・予定を確かめる・連絡する）と、[背景・課題](./requirements.md#12-背景課題)の解決に直結するものを上にする
   - **工数の小ささ**：価値が近いなら、早く届けられる小さいものを上にする
   - **依存関係**：他のストーリーの前提になるもの（US-07 ログイン）は、**それを必要とするストーリーと一緒に**上げる（今回は会員機能がないので上げない）

- **US-03 が2位**：「推しのことを知りたい」というファンの動機に一番近く、2.5h と小さく作れるため
- **US-06 が3位**：公式の窓口としてファンとチームをつなぐ機能で、届いた問い合わせが次に作るべき機能のヒントにもなるため
- **US-02 が4位**：1h と小さいが、チーム紹介はメンバー一覧でもある程度伝わるので、Must の中では一番下にする
- **US-04 が Should**：ログイン不要で小さいので、予定より早く終わったときに足す
- **6位以下の並び**：次のリリースは US-07（ログイン）から始める。そのあとは[工数見積もり 4章](./04_estimate/estimate.md#4-遅れたときに削る順番)と同じ考え方で、購入 → 会員機能 → ダンサー → 管理者 → 推奨機能の順
- **ダンサー・管理者の機能が下位**：MVP のメンバー・出演予定は、管理画面がなくてもシーダーでデータを入れれば表示できるため。お問い合わせの内容は、管理画面（US-20）ができるまでは通知メールと phpMyAdmin で確認する

## 4. ストーリーポイント（SP）

初版は工数から機械的に決めています。

| 3 | 3〜4.5h | US-06 お問い合わせ |

## 5. スプリントの進め方

### 5.1 スプリント中のイベント（1人用に簡略化）

| イベント | いつ | やること |
|---------|------|---------|
| スプリントプランニング | 各スプリントの最初 | この計画を見て、スプリントの Issue を「Todo」に移す。前のスプリントの残りがあれば入れ替える |
| デイリースクラム | 作業を始めるとき | ボードを見て「前回やったこと・今回やること・困っていること」を確認する |
| スプリントレビュー | 各スプリントの最後 | スプリントゴールを達成したか、ブラウザで実際に操作して確認する |
| スプリントレトロスペクティブ | Week 24 の最後 | 3スプリント分をまとめて振り返る（計画と実績の差、ベロシティ、次に活かすこと） |

### 5.2 完了の定義（Definition of Done）

ストーリーの Issue を「Done」に移してよいのは、次をすべて満たしたときです。

- [ ] Issue に書いた受け入れ条件をすべて満たしている
- [ ] Feature Test を書き、ローカルでテストが通っている
- [ ] スマートフォン幅（375px）とPC幅で表示が崩れていない
- [ ] 機能ごとのブランチ（例：`week23/member-list`）から PR を作り、main にマージした
- [ ] 実際に作業した時間を Issue にコメントで残した（振り返りで見積もりと比べるため）

### 5.3 遅れたときのルール

- 予備がないため、各スプリントの半分の時間が過ぎた時点でボードを確認する
- 遅れたら、まず US-02 チーム紹介を次のリリースに回す（Must の中で一番順位が低いため。Sprint 1 で遅れた場合は Sprint 3 の最後に回す）
- それでも足りなければ、カレンダー（US-01b）を「月ごとのリスト表示」に切り替える（[工数見積もり 5章](./04_estimate/estimate.md#5-リスク時間がかかりそうなところ)）、お問い合わせの確認画面を省き「入力 → 完了」にする、の順で範囲を小さくする

## 6. カンバンボード（GitHub Projects）

### 6.1 ボードの構成

| 列（Status） | 入れるもの |
|-------------|-----------|
| Backlog | まだスプリントに入っていないストーリー・タスク（今回作らないものもここに残す） |
| Todo | 今のスプリントでやるもの（スプリントプランニングで移す） |
| In Progress | 作業中のもの（同時に 2 つまで） |
| In Review | PR を作ってセルフレビュー中のもの |
| Done | 完了の定義（5.2）を満たしたもの |

### 6.2 Issue の付け方

- ユーザーストーリー 1 つにつき Issue を 1 つ作る（タイトル例：`[US-03] メンバー一覧とプロフィールを見たい`）。US-01 は分割した US-01a・US-01b の 2 つにする
- ラベル：`user-story`、MoSCoW（`must` / `should` / `could`）、利用者（`fan` / `member` / `dancer` / `admin`）
- マイルストーン：`Sprint 1`〜`Sprint 3`（今回のスプリントに入るものだけ。Should・Could はマイルストーンなし）
- Week 21 で、各ストーリーを作業単位に分けたタスクの Issue と、技術タスク（TECH-01〜03）の Issue を追加する
