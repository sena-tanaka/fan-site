# スプリント計画（Week 22〜24）（Week 21 確定版）

> 各作業の工数は [工数見積もり](./04_estimate/estimate.md) を参照。機能ID は[要件定義書 5章](./requirements.md#5-機能要件一覧)と同じ。
> タスクは GitHub Issues で管理し、GitHub Projects のボードに載せている（ボードの URL は README を参照）。

## 1. 全体の流れ

使える時間は3スプリント合計で 26h。Week 22〜24 はレッスンの区切り（スプリント1〜3）で、カレンダー上の週とは一致しない。

| スプリント | テーマ | ゴール（このスプリントの終わりにできていること） | 工数 |
|-----------|--------|----------------------------------------|-----:|
| Week 21 | 設計の確定 | 設計書一式・Figma・GitHub Issues と Projects のボードがそろっている | — |
| **Week 22（スプリント1）** | 土台とチーム情報 | ログインしないと入れず、ファンとダンサーでログインでき、トップ・メンバー一覧・出演スケジュールが見られる | 10.5h |
| **Week 23（スプリント2）** | ブログとお問い合わせ | ダンサーが写真付きでブログを投稿・編集・削除でき、ファンがメンバーごとに読める。お問い合わせを送れる | 8.5h |
| **Week 24（スプリント3）** | いいね・仕上げ | ブログにいいねでき（Ajax）、本番環境で全機能が動く | 5.5h ＋ 予備 1.5h |

- Week 22〜23 で MVP（いいね以外の Must、要件定義書 3章）を完成させる
- 土台（DB・ログイン・ロール）を最初に作り、ブログ（必須機能の大部分を担う）を真ん中のスプリントに置いた
- Week 24 は作業量を少なめにして、予備を集めている。遅れが出たら Week 24 で吸収する

## 4. 進め方のルール

- 作業は GitHub Issues 1つにつき1ブランチで行う（例：`week23/blog-crud`）。1機能ごとに PR を作ってマージする（Week 5 以降と同じ流れ）
- GitHub Projects のボードは「Todo → In Progress → Done」で動かし、作業を始めたら In Progress に移す
- 各スプリントの最後に、実際にかかった時間を Issue に記録し、見積もりとのずれを確認する。予備を超えそうなら、[工数見積もり 4章](./04_estimate/estimate.md#4-遅れたときに削る順番) の順で削る
- 予備時間は前倒しで使わず、遅れの吸収に使う。Must がすべて終わって予備が残ったときだけ Should に進む
