# 工数見積もり（機能別工数表）（Week 21 確定版）

> スケジュールは [sprint-plan.md](../sprint-plan.md) を参照。機能ID は[要件定義書 5章](../requirements.md#5-機能要件一覧)と同じ。

## 1. 見積もりの前提

- 単位は時間（h）。0.5h 刻み
- 1つの機能を「画面（Blade・CSS・JS）」「処理（ルート・コントローラー・FormRequest・Policy）」「テスト（Feature Test）」の3つに分けて見積もる
- **開発に使える時間は、3スプリント（Week 22〜24）合計で 26h**
- Week 7〜17 で作ったもの（ブログ CRUD・Breeze・Policy・画像アップロード・CI・AWS へのデプロイ）は流用・参考にできるので、初めて作るより短く見積もっている
- 予備を 1.5h 残す。遅れたときは 4章の順番で削る

## 4. 遅れたときに削る順番

コースの必須機能（要件定義書 1.8）を担う機能は削らない。削るのは、次の「仕上げ」と「範囲」だけにする。

1. レスポンシブ調整を最低限にする（スマホ幅で崩れないことだけ確認） … −0.5h
2. お問い合わせのテストを省く … −0.5h
3. お問い合わせで、名前・メールにログイン中の値を最初から入れておく処理を省く … 約 −0.25h
4. ログイン画面のチーム紹介をメインビジュアルなしの文章だけにする … 約 −0.25h

テスト（NF-19）は、ログイン必須化・PostPolicy・いいねの3つは必ず残す。

## 5. リスク（時間がかかりそうなところ）

| リスク | 影響する機能 | 対策 |
|--------|-------------|------|
| 本番で画像が表示されない（storage:link・ディレクトリの権限） | F-19 | スプリント2で画像アップロードを作った時点で、本番にも一度デプロイして確認する |
| Ajax の 419（CSRF）・401 で、いいねが動かない | F-18 | ルーティング設計 3章の形で、`X-CSRF-TOKEN` と `Accept: application/json` を最初から付ける。ブラウザの開発者ツールでレスポンスを確認しながら作る |
| ログイン必須化で、ログイン画面までリダイレクトのループになる | F-29 | Breeze のルート（`routes/auth.php`）は `auth` グループの外に置く（ルーティング設計 2章） |
| ダンサーとメンバーのつながり（users.member_id）を間違え、絞り込みが動かない | F-32 | Seeder でダンサーのアカウントと members を必ずセットで作る |
| 予備が 1.5h しかない | 全体 | 各スプリントの最後に残り時間を確認し、超えそうなら 4章の順で削る |
