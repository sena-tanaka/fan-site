# 工数見積もり（機能別工数表）

> スケジュールは [schedule.md](./schedule.md) を参照。機能ID は[要件定義書 3章](../requirements.md#3-機能要件一覧)と同じ。

## 1. 見積もりの前提

- 単位は時間（h）。0.5h 刻み
- 1つの機能を「画面（Blade・CSS・JS）」「処理（ルート・コントローラー・Service・Repository）」「テスト（Feature Test）」の3つに分けて見積もる
- Week 7〜17 で作ったもの（ブログ CRUD・Breeze・Policy・S3・Stripe・CI・デプロイ）は流用・参考にできるので、初めて作るより短く見積もっている
- 初めてのもの（Stripe Webhook、在庫の同時購入対策、カレンダー表示、Ajax で JSON を受け取る画面）は長めにしている
- **1週間に使える時間は 35h と仮定**（平日 4h × 5日 ＋ 休日 7.5h × 2日）。実際に使える時間に合わせて Week 21 で見直す

## 3. 合計

| 優先度 | 工数 | 3週間の使える時間（105h）に対して |
|--------|-----:|------|
| 必須 | 89h | 必ず入れる |
| 推奨 | 12h | 必須が終わってから（予備時間を使う） |
| 任意 | 6.5h | 今回の計画には入れない |
| **必須＋推奨** | **101h** | 予備は 4h しかない |

必須だけなら 16h（約15%）の予備が残る。推奨は「予備から使う」扱いにして、遅れたら推奨から削る。

## 4. 遅れたときに削る順番

1. 任意（F-13 カート、F-25 ダンサー用アカウント発行）… もともと計画に入れていない
2. 推奨のうち管理画面の一覧系（F-27 お問い合わせ一覧、F-28 注文一覧）… phpMyAdmin で代わりに確認できる
3. F-26 動画管理 … シーダーで登録すれば表示はできる
4. F-21 いいね数の確認、F-15 購入履歴
5. F-18 いいね … ここまで削るとブログの価値が下がるので最後

## 5. リスク（時間がかかりそうなところ）

| リスク | 影響する機能 | 対策 |
|--------|-------------|------|
| Stripe Webhook をローカルで受け取れない | F-12, F-14 | Stripe CLI の `stripe listen --forward-to` を使う。Week 22 のうちに一度動かしておく |
| 本番だけで起きる不具合（S3 の権限、メール送信、HTTPS） | 全体 | Week 22 の最後に「何もないページ」を一度デプロイし、最終週にまとめてデプロイしない |
| カレンダーの表示に時間がかかる | F-07 | ライブラリ（FullCalendar）を使う。うまくいかなければ「月ごとのリスト表示」に切り替える |
| テストが後回しになる | NF-19 | 各機能の工数にテスト時間を入れ、機能ごとに書く。最終週の 3h は不足分の追加だけ |
